# Unity内部で先に進める作業

更新日: 2026-10-23。公開共有箱庭の[全体設計](unity-shared-sandbox-draft_ja.md)から、共通ProtocolやClient Libraryの実装を先取りしない作業を切り出します。

## 1. 先行作業の目的

Unityの表示・操作・端末性能について、共通化の結果を待つ必要のない部分を先に確かめます。成果物は材質、mesh、描画部品、ローカルのデモシーン、座標表示の計算、Web buildの観測です。

Unity内のC#スクリプトでブロックを配置するデモは作れます。このC#コードはUnityの内部処理であり、Minecraft RemoteのC# Client Libraryを実装するものではありません。

共通の型・codec・API・fixtureが用意されたら、その入力をUnityの表示へつなぐadapterを追加する構成を目指します。今のローカルデモの形式を、後のProtocolや同期形式へ採用する前提にはしません。

### 1.1 体験品質を育てる反復

ローカル建築デモの先行確認は、最終の学習体験を育てる開発として扱います。材質の見分けやすさ、個数の数えやすさ、移動・照準の感覚、操作中の負荷は、実際に触って判断する部分です。小さな同じ建築場面で設定を変え、比較しながら整えます。

| 観点 | 触って確かめること | 後の連携でも使う成果 |
| --- | --- | --- |
| 材質と境界 | 10個の列や壁を正面・斜めから見て数えられるか。反射や透明感で境界が消えないか | 材質、輪郭の表現、照明の設定、比較用の建築場面 |
| 空間と移動 | 建築へ近づき、周りを歩き、上部を見たときに形と大きさを把握できるか | カメラ・移動・当たり判定の部品と調整値 |
| 照準と座標 | 狙ったブロックと表示座標が対応し、面の端や負の座標でも迷わないか | 対象セルの計算、強調表示、HUDの配置 |
| 表示更新と負荷 | 配置・置換・除去や表示数の増加で、見回しや座標の読み取りが妨げられないか | 描画・更新の部品、性能の測定結果 |
| Webでの体験 | 同じ場面を対象端末のbrowserで開き、入力や文字の読みやすさ、ロードを確認する | Web用の設定と端末ごとの観察結果 |

一度に全項目を完成させず、例えば「鉄の壁の個数を斜めから数えられるか」のように、一回の比較で見る点を絞ります。場面・設定・端末と、見分けられたところや迷ったところを残し、次の調整へ使います。

後へ残すのは、assetや内部部品に加え、体験上の判断とその理由です。共通化の成果をつなぐ際に内部コードの調整が必要になっても、これらの観察を設計の入力として使えます。

## 2. ロードマップとの関係

| Phase | 担うこと | Unityの先行作業との関係 |
| --- | --- | --- |
| D | 言語ごとの開発体験、catalog・型・補完などの評価 | 材質や画面の読みやすさを調べる。C# APIやcatalogの投影方式は決めない |
| E | Python・Java・Protocol等を比較し、意味のownerと投影を整理 | 共有の操作意味論をUnity用に独自確定しない |
| F | 既存fixture・executable contractを独立実装にも使えるconformance基盤へ一般化 | Unity独自のcodecや互換testを先に正本化しない |
| G | TypeScript Nodeの独立実装 | Nodeの通信処理をUnityの表示試作へ持ち込まない |
| H | Browser/WebSocketでのTransport独立性と既存Bridge境界の検証 | Unity Webの描画・入力・メモリの確認は進められる。WSS疎通やroutingの完了とは区別する |
| I | 一般用途C# Client LibraryとUnityへの展開 | 共通化の入力を使う連携部分は、この進行に合わせる |

D/E/Fを進め、G/H/Iを並行に近い形で始める可能性は検討中です。この文書では順序を改訂せず、全てのPhaseを独自に直列完了待ちにする条件も追加しません。連携へ進むとき、対象機能に必要な共通contract・型・fixture・検証方法と、合意した着手範囲を確認します。

世界定数のhello配送とHUDのstream選択も共通の計画に従います。先行シーンでは値をローカルに与えて表示を調べ、同じ機能の独自APIを作りません。

| 要素 | 作る・調べるもの | 確認する結果 | 共通化を待つ境界 |
| --- | --- | --- | --- |

| Unity Web build | 同じデモをWebへ書き出し、ブラウザで動かす | 初回ロード、入力、メモリ、描画が実機でどうなるか分かる | 公開/LANの配布、認証、TLS、Bridge、接続設定 |
| 手作業の操作感（後続候補） | 照準面の隣へ置く位置のpreview、クリックやタッチの操作 | 手で積む入口の操作が分かりやすい | 正式な編集要求、認可、サーバー更新、全員への反映 |

### 3.1 ブロックの見た目

材質を並べた比較シーンを先に作れます。単独の立方体だけでなく、柱、床、壁、階段として隣接させ、個数を数えられるかを見ます。

- 金と鉄は色だけでなく反射の具合も比較する。
- シーランタンは発光して見える材質から試す。各ブロックを個別の実時間ライトにすることを前提にしない。
- ガラスは透明感と輪郭を比較し、奥に重なった個数の見え方も確認する。
- 草は地面と追加の立方体として使い、上面と側面を区別する。
- TNTは見た目を用意する範囲に留め、爆発・火・物理の意味を先に決めない。

ここで作るのはUnityのassetです。正式なcatalogやblock stateを代用する独自のID一覧・schemaを公開しません。

### 3.2 地面と座標の基礎

1ブロックの辺をUnityの1単位として扱う案から、表示の寸法を揃えます。整数セルが各軸の区間`[n,n+1)`を表すなら、Unityの中心基準のcubeの描画位置はセル座標に`0.5`を加えます。これは描画側の変換で、APIへ隠れた座標offsetを追加するものではありません。

草の最上段セルy=62の上面をy=63とし、そこに足の基準点を置きます。カメラや身体の中心を足の座標として表示しません。負の位置を整数セルへ変換する際は各軸をfloorし、単純な切り捨てで0側へ寄せません。

9原点、地面の高さ、導入用origin`(100,0,100)`などは、ローカルシーンの設定として与えます。将来helloから得る世界定数やserver正準originを差し込めるようにし、通信先の設定や正式な世界定数providerをここで再実装しません。

区画の辺や外周の配置案を、画面で比較することもできます。見た目のガイドやローカルな移動制限は、サーバーが建築を許可・拒否する規則を確定した証拠にはしません。

### 3.3 足・照準のHUD

足の点を含むセルと、照準が当たったセルを別々に表示します。地面を指したときは、足のy=63と地面のy=62を読める状態にします。照準が何にも当たらないときは`—`を表示します。

相対表示にはローカルに与えたoriginを使います。例えば足が絶対`(120,63,130)`、originが`(100,0,100)`なら相対`(20,63,30)`です。値の入れ替えで表示を確認するだけにし、stream選択の通信や仮のWireScope IDを作りません。

表示の大きさ、改行、色、視認性、画面を狭くしたときの配置は先に比較できます。表示に必要な位置・originをどの接続から得るかは、後から共通のHUD/認証の契約へ接続する部分です。

### 3.4 描画と性能

少数のブロックを単純に表示する比較基準を用意し、数を増やして描画方式を評価します。meshのまとめ方、GPU instancing、見えていない面や範囲を描かない方法は、Unity内部で比較できる候補です。最初から一つへ固定せず、実機で差を見ます。

表示用のセル保持やmesh生成単位は、描画を測るための内部構造です。そこからネットワーク用のchunk境界、同期payload、world databaseの形式を決定しません。400×400×256の全セルをGameObjectとして作ることも前提にしません。

確認結果には、表示ブロック数、材質、影、透明なブロックの重なり、端末/OS/browser/Unity版、初回ロード時間、フレーム時間、メモリなどを残します。測定対象の端末と目標値を決める前に、低性能PCやタブレットでの動作を保証しません。

## 4. 通信を使わないローカルデモ

ローカルのC#スクリプトやInspectorで、固定の建築場面を描画部品へ与えます。Protocol clientの代役や、仮の公開箱庭サーバーは用意しません。

| デモ | 見ること |
| --- | --- |
| 1個と10個の柱 | 1ブロックの寸法、隣接境界、個数の読みやすさ |
| 壁・階段・小さなピラミッド | 見回し、奥行き、遮蔽、材質の区別 |
| 同じセルの表示を差し替える | 古い見た目が残らないこと |
| 一部を取り除く、場面を入れ替える | 表示の更新とローカルな初期化 |
| 草の地面と小さな建築 | 歩行・当たり判定、足と照準の座標 |
| 表示数やガラスを増やす | 描画負荷・メモリ・操作感の変化 |

このローカル入力には、hello、token、method名、JSON-RPC envelope、TCP/WebSocket、独自のsnapshot/delta schemaを含めません。描画部品へ必要なセル位置やasset参照を普通のUnity内部データとして渡します。入力用の関数や型は内部のものにし、将来のSDKや表示同期の公開interfaceとして固定しません。

ローカルの「場面を初期化する」動作は、共有世界のリセットや再接続の意味論とは別です。複数ブラウザの同期、reset前後の要求の順序、処理の完了通知はここでは扱いません。

## 5. 着手する順番の案

| 順番 | 作業のまとまり | 区切りとして確認すること |
| --- | --- | --- |
| 1 | ブロック材質と少数配置の比較シーン | 6種類の基本ブロックを見分け、柱や壁の個数を数えられる |
| 2 | 地面・9区画・移動・照準・ローカルHUD | 世界原点と導入用origin、草y=62と足y=63、負の座標の表示が整合する |
| 3 | 同じシーンのWeb buildと実機確認 | Editorだけでなく、想定browserでも描画・移動・表示が動く |
| 4 | 表示更新と描画方式の比較 | 追加・置換・除去を繰り返し、負荷と見た目の違いを記録できる |
| 任意の後続 | 手作業のpreviewと操作の比較 | 手で置く練習に必要な入力と照準の対応を確かめられる |

最初の区切りは、通信なしで「草の地面に学習用のブロックを並べ、歩いて数え、足と照準の座標を読む」シーンです。Web buildもこの小さなシーンから試し、400×400の世界を多数のブロックで埋める負荷試験とは分けます。

成果物は、Unity用の作業場所で作るasset・scene・内部スクリプトと、観測した条件/結果です。Unity用repoやpackageの配置は未決です。一般用途C# libraryの`src/`へUnity依存を加えず、server projectやNuGet/release設定も先行作業には含めません。

## 6. 共通化の入力を待つ部分

| 部分 | 待つ入力・判断 |
| --- | --- |
| C# Client Libraryの通信実装 | Phase E/Fで整理するProtocolの意味・型・fixture・conformanceと、C#の着手範囲 |
| 4操作を受ける箱庭サーバー | operationの意味、result/error、未対応範囲、認証・permission・build guard等 |
| helloと世界定数 | 非Minecraftのmetadata、定数の配送schemaと各clientの投影 |
| catalogとblock値 | 正式なID/state、対応するsubset、C#への自然な投影と表示assetの対応 |
| HUDのstream選択 | APIのexact contract、本人/閲覧者とstreamの対応、WireScope IDの扱い |
| 共有表示の通信 | 初期状態、更新、再参加、順序、リセットの意味と、表示同期のowner |
| Bridgeとbrowserの接続 | Phase HのTransport独立性・Origin/routing境界、公開/LANの設定contract |
| 本番の配布・起動 | 成果物のowner、互換set、公開/LAN/PC1台の起動・設定・更新・診断 |

前の表の作業は、これらのcontractを迂回するための別実装ではありません。未知の部分を仮のRPCやJSON形式で埋めて接続デモを先に完成させると、後で共有資産を使いにくくなるため、ローカルな表示入力のところで止めます。

## 7. 連携へ移るときの引き継ぎ

- 共通の型から、セル位置・描画するasset・変更内容へ写すadapterを追加する。共通型の意味は変えない。
- デモ用の配置を、共通fixtureに基づく入力と接続した場合も、画面側の計算・材質・性能の観測を再利用する。
- 共通fixtureとの対応が必要な部分は、対象のcontractとfixtureの版を明示して検証する。ローカルな見た目の確認をProtocol conformanceの代わりにしない。
- Unity内部のmeshやcacheを、サーバーの正本、Protocolのvalue型、送信単位へ自動昇格させない。
- 自前の通信stubを温存して二系統を育てる構成を作らない。
